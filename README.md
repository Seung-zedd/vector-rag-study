# Vector DB & RAG Study

## 학습 원칙

각 레슨은 개념을 충분히 대화하고 이해한 뒤에만 문서화합니다.

목표는 API를 외우는 것이 아니라 다음을 할 수 있게 되는 것입니다.

- 개념을 설명한다.
- 실제 시스템을 관찰한다.
- 결과를 검증한다.
- 다른 프로젝트와 연결해서 재사용한다.

## 레슨 파일 분할 규칙

학습 문서의 가독성을 위해 **Markdown 파일 하나가 500라인을 초과하면 동일한 레슨 폴더에 새 파일을 만들어 내용을 분할**합니다.

- 파일명은 레슨 폴더 안에서 `01-주제.md`, `02-주제.md`, `03-주제.md`처럼 **두 자리 순번 + 주제명**으로 지정합니다.
- 기존 파일이 500라인을 넘기기 전에 자연스러운 주제·절 경계에서 분할합니다. 코드 블록, 수식, Q&A, 표를 중간에 자르지 않습니다.
- 각 분할 파일은 **500라인 이하**를 목표로 유지하고, 새 내용으로 초과할 경우 다음 번호의 파일을 생성합니다.
- README 목차와 파일 간 이전/다음 링크를 함께 갱신해 학습 순서가 이어지도록 합니다.
- 각 파일의 Glossary 및 References는 해당 파일의 내용에 맞춰 관리하고, 출처 추적성을 유지합니다.
- 기존 장문 파일도 후속 정리 시 이 규칙에 맞게 분할합니다.

## 공개 및 저작권 판단 원칙

이 저장소는 **개인 학습과 독자적으로 도출한 기술 아이디어를 공개 가능한 형태로 정리**하는 공간입니다.

### 공개 가능

- 공개 논문·문서·표준을 바탕으로 학습한 일반 기술 개념
- 개인적으로 고안한 설계 아이디어, 알고리즘 비교, 디자인 패턴 응용
- 서로 다른 분야를 연결한 `Connecting the Dots` 및 Q&A
- 독립적으로 작성한 synthetic example과 일반화된 코드 예시

### 공개 금지 또는 사전 확인

- 회사의 실제 데이터셋, 비공개 API 응답·엔드포인트, credential, secret
- 회사의 내부 운영 환경, 비공개 소스코드·설정·문서
- 회사 소유의 비공개 설계·구현 세부사항 및 식별 가능한 고객·사업 정보
- **개인적으로 생각해 낸 아이디어라도 업무상 개발한 결과물에 해당할 수 있는 경우:** 고용계약, 사내 규정 및 지식재산권 귀속 조건을 확인하기 전에는 공개하지 않음

### 문서화 전 점검

1. 내용이 공개 지식 또는 독립적으로 설명 가능한 개인 학습·설계 아이디어인가?
2. 실제 회사 데이터·식별자·인프라·내부 구현 세부사항이 섞이지 않았는가?
3. 업무상 저작물이나 회사의 비공개 자산에 해당할 여지는 없는가?
4. 불확실하다면 구체 내용을 제거하고 일반화하거나, 공개 가능 여부를 먼저 확인했는가?

> **핵심:** 개인의 학습 성과와 독창적 사고는 기록하되, 회사 기밀 및 제3자의 권리는 침해하지 않는다. 독창성만으로 업무상 결과물의 공개 권한이 자동 보장되지는 않는다.

## References 작성 원칙

각 Lesson은 **Glossary 다음, 문서의 맨 아래에 `## References`**를 둡니다.

- **Primary Sources:** 논문, 원저작물, 학술 자료
- **Official Documentation:** 공식 기술 문서 및 표준
- **Related Public Study / Further Reading:** 실제로 연결한 공개 학습 노트와 보조 자료
- 관련성 있는 공개 자료만 기재하며, 출처를 확인하지 않은 내용을 특정 논문의 주장으로 표시하지 않습니다.
- 원문을 장문 복제하지 않고 독자적인 설명을 작성합니다. **인용·출처 표시는 사용 허가나 기밀 공개 승인을 대신하지 않습니다.**
- 개인적인 가설, 비유, 설계 응용은 원자료의 주장과 구분합니다.
- 회사의 비공개 자산이나 업무상 결과물은 출처 기재 여부와 무관하게 기존 **공개 및 저작권 판단 원칙**을 적용합니다.
